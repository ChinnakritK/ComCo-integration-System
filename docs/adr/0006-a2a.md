# ADR-0006: Agent-to-Agent (A2A) with the official a2a-sdk

**Status:** Accepted · **Phase:** 3

## Context
Requirement 4.4: a multi-agent architecture (Coordinator, Customer Agent, Order Agent) showing agent
discovery and capabilities, task delegation, task execution, task result/status and multi-agent
coordination, using an open A2A protocol/SDK or equivalent.

## Decision

### Protocol and SDK
The **A2A protocol v1.0** (Linux Foundation project, originally contributed by Google) through the
official Python SDK **`a2a-sdk` 1.2.0**, JSON-RPC binding over HTTP. We verified the SDK end to end
(card, SendMessage, task lifecycle, artifacts, GetTask) before adopting it; the implementation is
not a look-alike protocol.

### Roles
| Agent | A2A role | Skills (from its Agent Card) | Gateway identity |
|---|---|---|---|
| Coordinator | A2A **client**; also the Agent API behind Kong | - (plans and delegates) | - in A2A mode |
| Customer Agent | A2A **server** | `get_customer` | consumer `customer-agent` - Customer API only |
| Order Agent | A2A **server** | `get_order`, `get_latest_order`, `list_customer_orders` | consumer `order-agent` - Order API only |

### Interaction
```
Coordinator                                 Customer Agent / Order Agent
───────────                                 ────────────────────────────
start-up & on demand:
  GET /.well-known/agent-card.json  ───────▶ Agent Card {name, skills[], supportedInterfaces[/a2a]}
  build skill → agent map (cache 30 s, re-fetch when an agent was unreachable)

per planned step (from the LangGraph plan):
  POST /a2a  SendMessage                     Task SUBMITTED
    Message(role=USER,                       ├─ WORKING   "Calling get_latest_order {...} via the API gateway"
      parts=[DataPart{skill, args}],         ├─ GET kong:8000/api/v1/orders/latest (own API key)
      metadata={correlation_id})             ├─ Artifact  DataPart = normalised ToolResult
                                             └─ COMPLETED | FAILED | REJECTED | INPUT_REQUIRED
  ◀─────────────────────────────────────── Task {id, contextId, status, artifacts}
  map artifact → step result; dependency rules decide the next step
```

* **Discovery & capabilities** - the Coordinator knows only base URLs (`A2A_AGENT_URLS`). Routing is
  derived from the skills advertised in each Agent Card, so adding a skill to an agent needs no
  coordinator change. `GET /api/v1/agent/agents` shows what was discovered and what is reachable.
* **Delegation** - one A2A task per planned step. Structured `DataPart {"skill","args"}` is used
  between agents (unambiguous, validated); the specialists also accept free text, so any A2A client
  can use them ("latest order of customer C001").
* **Result/status** - the final task state is part of every step in the Agent API response
  (`steps[].a2a.state`, `task_id`), and `GET /api/v1/agent/a2a/tasks/{agent}/{task_id}` fetches the
  task from the agent with A2A `GetTask` (history, status message, artifacts).
* **Coordination** - the Coordinator combines results from several agents and applies dependency
  rules (no Order Agent task for a customer the Customer Agent reported as non-existent).

### Task state semantics
| Specialist outcome | Task state | Rationale |
|---|---|---|
| data found | `COMPLETED` | |
| entity does not exist (404) | `COMPLETED` | a definitive business answer, not an agent failure |
| API unavailable / timeout / 429 | `FAILED` | artifact carries HTTP status and error code |
| skill not offered / bad arguments | `REJECTED` | |
| free text without an ID | `INPUT_REQUIRED` | multi-turn capable; asks for the ID |

### Failure handling
| Failure | Detection | Result |
|---|---|---|
| Agent container down | connection error on card fetch or SendMessage | step `unavailable`, `AGENT_UNAVAILABLE`; answer says the agent is not reachable; other agents' results still returned (`partial`) |
| Agent slow | A2A client timeout (12 s) | `AGENT_TIMEOUT` |
| Backend down behind an agent | task `FAILED`, artifact has HTTP 503 | answer says the Order *service* is unavailable |
| Agent restarts | card re-fetched on next request | recovers automatically (tested) |

### Why A2A traffic does not go through Kong
Kong is the **north-south** boundary (external consumers → platform). Agent-to-agent calls are
**east-west** traffic inside the platform network, like service-to-service calls. Every agent's
access to *business data* still goes through Kong under its own least-privilege identity. In
production the A2A hop would be secured with mTLS (service mesh) and/or the Agent Card
`securitySchemes` (e.g. OAuth2 client credentials), and could optionally be routed through an
internal gateway for rate limiting.

### Observability across agents
The Coordinator's A2A HTTP client injects `traceparent` and `X-Correlation-ID`; the specialists run
the same middleware, and their Kong calls carry both again. One trace in Jaeger therefore shows
`kong-gateway → coordinator-agent (plan, a2a steps) → customer-agent / order-agent → kong-gateway →
customer-service / order-service → SQL`, and one correlation ID finds every log line.

The SDK's built-in spans (`OTEL_INSTRUMENTATION_A2A_SDK_ENABLED`) are switched off: they add ~110
internal spans per request and record the SDK's normal end-of-stream signal (`QueueShutDown`) as an
error, which would show every successful task in red. Each specialist instead emits one span per
task, `a2a.task <agent>`, with `a2a.task_id`, `a2a.skill`, `a2a.state` and the correlation ID; only
genuinely failed tasks are marked as errors.

## Consequences
* Two extra containers, but each agent is independently deployable, replaceable (any A2A-compliant
  agent advertising the same skill works) and least-privileged.
* The same tool code (`comco_agentkit.tools`) runs in the coordinator (direct mode) and in the
  specialists (A2A mode) - no duplicated business logic. `EXECUTION_MODE=direct` keeps the Phase 2
  path available for comparison.
* Tasks are held in an in-memory task store per agent (lost on restart) - fine for a prototype;
  production would use the SDK's database task store.
* Streaming and push notifications are not used; tasks here complete in milliseconds.
